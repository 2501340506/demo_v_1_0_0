# 按键功能修改以来的问题与经验

## 结果与证据边界

2026-10-03 用户确认当前功能表现良好、稳定性可接受，作为 v0.1.0 归档。最终改动集中在 sd_card_bmp.v。仿真验证逻辑行为，上板反馈验证实际可用性；两者均不代表时序完全收敛，也不能倒推所有历史故障都出自同一个根因。

## 问题、证据与做法

| 阶段/现象 | 查明或推测的机制 | 处理与验证 |
| --- | --- | --- |
| 音频正常但首图黑屏 | 两个完成事件到达顺序不同可能丢失；ready 只是空闲，不代表已读完 | 观察源端进入忙态后再判断完成，独立锁存双方完成，汇合后提交 |
| 切图后永久等待 | 仿真注入图头错误，BMP 返回空闲但未发写请求，上层却等写完成 | 记录是否发起写入；未写失败退出，已写任务仍等待，防止覆盖在途缓冲区 |
| 写应答跨域 | 接收端直接使用另一时钟域电平 | 两级同步应答；该方案依赖发送端保持电平直到请求撤销 |
| 首图及 KEY1 改善、KEY2 短长按仍不稳定 | 事件生成和 pending 更新交错，边界复杂；没有板上逐拍证据证明唯一根因 | KEY1/KEY2 统一稳定边沿，KEY2 两态状态机输出单拍短/长事件，用户最终反馈稳定 |
| pending 消费与新事件同拍 | 非阻塞赋值最后一次生效，或 !pending 条件屏蔽了新事件 | 先消费，再无条件捕获有效新事件；每方向仍只有一位，不形成队列 |
| 自动到期与手动冲突 | KEY2 注册事件延迟一拍，仅检查注册脉冲会遗漏产生事件的周期 | 自动入口同时避开稳定边沿、长按到期、事件脉冲和 pending |

## 最终控制约定

同步与消抖 → 稳定电平及上一拍 → 单拍事件 → pending → 加载仲裁。原始按键仅进入消抖模块。KEY1 按住不连发；KEY2 低于长按阈值释放才算短按，长按已触发后释放不再短按。加载完成后下一空闲拍消费 pending，使用新提交的图片编号计算目标。每方向请求合并，优先级不等于按键时间顺序。

不能把源端 ready、数字 1 或单一完成脉冲当作整帧成功。首图前数字 1 可代表空闲，提交后才是图片编号。不能以超时清 busy 代替写事务完成，否则可能覆盖仍在使用的缓冲区。

## 验证方法与遗漏

从两个方向请求计数扩展到四张图的实际启动顺序，避免两张图时“上一张”和“下一张”相同掩盖仲裁错误。用缩放周期覆盖 20 ms 消抖、1 秒长按和 3 秒轮播，测试保持、释放再按、阈值两侧、长短互斥、忙时请求、同拍消费与捕获、自动到期及图头失败。14 组测试通过，包含连续 20 轮加载。

按键测试驱动实际输入和消抖器；仲裁碰撞用局部 force 构造，不能将其说成完全自然输入测试。当前测试没有真实异步 SDRAM/FIFO 模型或亚稳态，时序报告 Setup WNS -6.699 ns 仍未关闭。今后若复现故障，应记录具体按键顺序、轮播状态和加载阶段，再根据证据定位。

## 工程协作经验

此前只改长按表达式和 pending 判断就描述为完成修正，实际上没有实现统一事件层；原有七组测试通过也不能证明新增行为已完成。验收应逐项核对代码结构和行为断言，明确区分计划、实现、仿真、构建、上板五个阶段。

终端工具应通过实际命令验证，不能因误用桌面接口就断言终端不可用。文档用显式 UTF-8；旧 HANDOFF 混合编码原始备份留在本地。仿真库、日志、锁文件不入版本，稳定 bitstream 与源码通过同一版本标签归档，历史说明应标注历史，避免旧的“待验证”覆盖最新验收结果。
